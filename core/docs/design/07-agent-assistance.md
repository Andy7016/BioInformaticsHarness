# 三层智能体协作与人类交接

日期：2026-10-02。来源：用户提出理论层、应用层、执行层的分工，并说明此前细分报告难以理解。三层方向及角色示例来自用户；下述交接规则与验收方式是本次设计细化。本文描述项目设计，尚未部署三层运行器或变更模型配置。

## 为什么需要应用层

研究中的技术报告需要有人读懂、比较、发现矛盾，并转化为对研究问题的回答。过去直接向用户交付细分报告，把这部分理解工作留给了用户。新增应用层承担这项工作，同时负责把抽象研究意图展开成具体方案。

理论层因此能够围绕研究目的、方法是否合理、结果意味着什么以及下一步如何选择与人交流。解释仍是理论层的职责：它需要理解应用层的分析，对重要判断负责，并根据人的疑问调整讲述。人不需要先读完底层报告才能参与讨论。

## 三层分别负责什么

| 层级与用户给出的模型示例 | 主要责任 | 向上交付 |
|---|---|---|
| 理论层：GPT-6-Astra | 理解人的目标，审视方法和系统设计，协调研究方向与资源，判断证据支持到哪里，与人解释和讨论重要取舍 | 清楚的研究解释、判断依据、局限与需要人参与的选择 |
| 应用层：GPT-6.1-Sol | 将方向展开为具体研究方案，分解任务，设定执行边界和验收方法，阅读执行证据，比较结果、解释差异并提出下一步建议 | 有证据索引的完整研究报告，以及可追溯原报告的摘要 |
| 执行层：GPT-5.6-Luna Max | 在清晰范围内完成检索、整理、代码实现、运行与检查；保留真实产物、失败及偏离 | 结果文件、执行记录、验证结果、资源消耗与未完成项 |

这些名称是角色配置示例，不构成模型能力或成本的实测排名。具体模型应通过任务质量、解释效果、成本和可用性验证后配置。角色职责与模型名称分别保存，允许替换模型而保持交接要求。

应用层需要研究判断能力：它必须能发现任务拆分是否偏离研究目标，识别相互冲突的结果，并说明可能原因及验证办法。执行层可自行处理范围内的实现细节和可逆修复；出现需要改变方法、数据范围、预算或授权的事实时，返回证据和待决问题。

## 从研究意图到结果解释

人的目标与约束交给理论层；理论层明确研究问题、方法依据、优先级和需要回答的疑问。应用层据此设计可执行的工作，说明输入、输出、约束、验收方法以及停止条件，再交给执行层。

执行结果返回后，应用层先对照验收要求检查产物，再组织研究分析。完整报告保留细节和来源；摘要突出结论、依据强弱、重要偏离、反证、未解决问题和建议。每项重要摘要结论应能定位到报告章节及其原始证据，报告绑定具体版本。

理论层阅读摘要，根据问题的重要性和不确定性回查完整报告与原始证据；证据冲突、异常或将影响关键决定的内容需要重点审查。理论层随后向人解释结果，也可要求应用层补充分析。新的目标或取舍再沿同一链条下达，形成反馈闭环。

分层汇报不能逐层丢失负面结果。影响判断的失败、方法差异、覆盖不足与分歧必须进入摘要；有分歧时分别保留观点、依据和可区分它们的检查。摘要流畅、上级认可或执行成功，都不能自动提升科学证据等级。既有独立验证与科学审阅责任仍然保留。

## 怎样与人交流

2026-10-04补充：[可视化解释](../ARCHIVE_POINTERS.md#archive-pointer-f41527062831f1f3)沿用三层分工。理论层确定需要解释的问题及判断边界；应用层选择生物材料、图形层次与叙述；执行层按规格调用工具、保留产物并检查图像。人看到的是有意义的图文说明，完整脚本和原始文件供追溯。

默认从“当前能判断什么、这对研究意味着什么”讲起，再解释必要依据与局限。首次出现的术语用日常语言说明；需要时用例子、对比或图示帮助理解。详细参数、对象编号、日志和来源索引留在可展开的报告中。篇幅随问题调整，不要求每次回复都填固定栏目。

启发性交流应帮助人理解选择之间的关系，例如说明为什么某个检查值得先做、不同结果将如何改变下一步。理论层应给出有依据的建议，明确何处需要人的价值判断，避免把所有技术选择都变成人的待办事项。人在需要时可以直接查看任何层的报告。

用户对现有报告难以理解的反馈，说明交接方式需要调整；它本身不能证明某个模型普遍不擅长表达。新的设计应实际检验：使用者能否说清当前研究问题、主要依据和下一步理由，而不是仅凭模型名称预期沟通效果。

## 在 mRNABERT 案例中如何交接

以下依据既有[可读过程说明示例](06-readable-process.md)展示职责分配，不表示本轮新增实验或重新核验结果。

执行层负责提交保存预测的指标复算结果、对应文件和检查范围。应用层将其解释为：这项检查回答“已有预测与所报指标是否一致”；重新加载模型生成预测属于另一项尚未完成的检查，原论文结果是否复现还需要比较实验条件。

理论层向人可以这样说明：

> 我们已经能核对保存下来的预测和分数。这让已有实验有了一个可以继续检查的起点。不过，还没有检查重新加载模型后能否得到同样的预测，所以目前只能确认保存结果可复核。下一步建议先确认模型、输入和预测之间的对应关系，再评估一次小规模推理检查是否可行。论文分数差异的原因仍需证据，暂时不能归因于模型或某个参数。

这样的交接同时保留进展、限制和下一步理由；需要追问时，应用层能提供具体技术解释和来源。

## 与现有 Harness 的连接

三层描述的是智能体之间的责任关系。已有方法、任务、执行模块描述系统功能；案例的“三层验收”描述证据检查范围。三者分别记录，避免将某一智能体层级等同于某一验收等级。

沿用现有对象即可表达初步设计：研究方向和选择关联 ResearchQuestion / Decision，应用任务关联 TaskDefinition，执行关联 Run / Attempt，完整报告和摘要关联 Artifact，审阅关联 Review。[可读过程说明](06-readable-process.md)仍是完整研究包的交付要求，报告、摘要与人类说明共享证据来源，避免重复建立事实库。

建议在交接记录中保存承担角色、实际模型配置、输入版本、输出引用、检查结果和未决项。模型和工具调用的实际消耗记入运行记录，汇总用于预算判断。小任务可以由同一智能体承担多个职责并明确记录，避免每次工具调用都经过三次转发；重要研究分析则保留应用层的消化与审阅步骤。

## 验收重点

1. 从人的目标能追到具体任务；执行者清楚范围、产物和停止条件。
2. 从理论层的重要判断能回查应用报告和原始证据，版本一致。
3. 注入一项失败或相互冲突的结果后，应用层摘要与面向人的解释仍呈现其影响，不会只剩成功结论。
4. 用户无需解读日志或对象编号，就能说明当前结论、依据、局限及下一步理由；读不懂时修订解释，保留原证据。
5. 完成任务与接受研究结论分别记录；三层内部一致不能替代独立检查或人的研究判断。

本轮仅形成职责与交接设计。尚待用真实案例验证沟通效果、信息损失和分层开销，再决定运行器接口与具体模型配置。
